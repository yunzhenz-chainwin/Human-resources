# 04. 履歷解析與匯入流程

**文件版本**：v1.1（2026-08-27）

> 文件定位：保存履歷合法取得、解析、OCR、校對與去重的流程基準；實際支援欄位、掃描政策與操作指令以程式、OpenAPI 及 [10-系統元件與資料庫使用手冊](10-系統元件與資料庫使用手冊.md) 為準。

## 1. 履歷的合法取得方式（前提）

| 來源 | 方式 | 說明 |
|---|---|---|
| 官方職涯網站（career_site） | 求職者於公開職涯站閱讀個資告知並勾選同意後，送出表單＋履歷檔 | **送出當下即自動建檔**（人才＋履歷檔；應徵指定職缺時連同應徵紀錄一次建立），不必等 HR 校對；履歷檔仍會列在解析佇列供 HR 後續校對 |
| 104 人力銀行 | 企業會員後台**手動下載**應徵者履歷 PDF / 主動開發下載 | 平台會員條款允許的正常使用 |
| 1111 人力銀行 | 同上 | |
| 求職者直接投遞 | Email 附件、紙本掃描 | |
| 內部推薦 | 推薦人轉交檔案 | 記錄推薦人於 `source_note` |
| 部門主管送交 | 主管於「送交履歷並指派職缺」選定本部門職缺後上傳 | 主管不可讀取原始檔與解析結果；HR 確認入庫後自動建立該職缺應徵紀錄 |

### 為什麼不做自動登入爬取？

1. **平台條款**：104 / 1111 會員條款禁止自動化程式抓取，違者企業帳號可能被停權——招募主要管道中斷的代價遠大於省下的下載時間。
2. **個資法風險**：以爬蟲繞過平台機制取得個資，蒐集手段的適法性有疑慮。
3. **技術成本**：反爬蟲對抗（驗證碼、行為偵測）維護成本高且不穩定。

### 替代方案（規劃中，尚未實作）：監控資料夾

構想：HR 在 104/1111 後台批次下載履歷到約定資料夾（如 `\\NAS\resume_inbox\104\`、`\resume_inbox\1111\`），
Watcher 定時掃描：發現新檔 → 排入解析佇列 → 成功移至 `processed/`、失敗移至 `failed/` 並通知，
讓 HR 唯一的手動步驟只剩「在平台按下載」。**目前系統未實作 Watcher**，現行做法為網頁批次上傳（見 §8）。

> 未來若採購 104 企業方案的 API 服務，可增設 `Api104Source` 介接層，架構已預留（來源與解析器解耦）。

## 2. 支援的輸入格式

| 格式 | 解析器 | 說明 |
|---|---|---|
| 104 履歷 PDF（文字層） | `p104` adapter | 依文字特徵簽章辨識版型，規則解析；目標欄位準確率 ≥ 95% |
| 1111 履歷 PDF（文字層） | `p1111` adapter | 同上 |
| 一般 PDF / Word（.docx） | `generic` adapter | 自由格式，準確率較低，低信心進校對；.docx 以 python-docx 抽取段落與表格 |
| 掃描影像 PDF | 本地 OCR（PyMuPDF 渲染 + Tesseract） | 已實作：文字層為空時自動 OCR（45 秒上限、20 頁上限），中文 OCR 文字先正規化；**OCR 結果一律進人工校對** |
| 舊版 Word（.doc） | 不自動抽取 | 檔案安全保存，標記 `needs_review` 走人工建檔或轉檔 |

上傳限制：僅接受 **PDF / DOC / DOCX**（multipart 可一次多檔，**不支援 ZIP**）、單檔上限 10 MB、空檔回 415；
檔頭簽章與副檔名不符回 415。所有上傳（含公開職涯站）先落到隔離區並做**惡意軟體掃描**（ClamAV / clamd）：
偵測到惡意內容回 422、掃描器不可用回 503（fail-closed）；只有 `APP_ENV` 為 development/test/local 且
`RESUME_SCAN_POLICY=allow_unavailable` 時才放行未掃描檔。正式環境（`APP_ENV=production`、`RESUME_SCAN_POLICY=fail`、
clamd `127.0.0.1:3310`）一律拒絕無法掃描的上傳。

## 3. 解析管線（Pipeline）

```
上傳（HR/主管網頁、公開職涯站）→ 掃毒與簽章驗證 → 同步解析（threadpool）
  → ①來源/版型判別 → ②文字抽取（含 OCR 後援）→ ③欄位抽取 → ④去重比對
  → ⑤信心計分 → 解析佇列（待校對/來源待確認）→ HR 確認入庫
```

| 步驟 | 做法 |
|---|---|
| ① 來源/版型判別 | 文字特徵簽章計分判定 p104 / p1111 / generic；分數不足即標記 `source_review_required`（來源待確認），由 HR 於校對介面人工指定（`PUT /resumes/{id}/source`），並保留判別依據 `source_evidence` |
| ② 文字抽取 | PDF 先讀 `pypdf` 文字層；文字層為空才以 PyMuPDF 渲染 + 本地 Tesseract OCR（不外送雲端），OCR 文字再做中文正規化；.docx 用 `python-docx`（段落＋表格）；.doc 不自動抽取 |
| ③ 欄位抽取 | 標籤錨點 + regex（Email、台灣手機、年資數字）與關鍵字啟發式；**現行 adapters（`adapters-2.2`）抽取欄位為：姓名、Email、電話、居住地、目前職稱、總年資、技能** |
| ④ 去重比對 | 見 §5 |
| ⑤ 信心計分 | 見 §6 |

> 規劃中（尚未實作）：區塊切分（工作經歷／教育背景／語文／證照／自傳）、民國年→西元年與期間/薪資正規化、
> 技能字串對映 `skills` 字典（目前僅做小寫正規化 `skill_norm`；管理端技能字典為獨立維護）。
> 另有「結構化 PDF」快速通道：系統產出的自製履歷內嵌簽章後的 `talenthub.resume.v1` 中繼資料，
> 簽章驗證通過直接高信心帶入欄位；簽章不符則降信心並強制人工校對。

## 5. 去重（Deduplication）

**比對鍵優先序（現行）**：

1. `file_hash`（SHA-256 全檔內容雜湊）相同 → 視為**重複檔案**：HR 上傳回 `duplicate=true`、介面顯示「重複檔案／相同檔案已存在人才庫，不會重複建立」，並在合法範圍內補上缺少的人才或職缺連結（已綁其他職缺/人才則回 409）；公開職涯站遇到屬於**他人**的相同檔案時，靜默捨棄檔案、只保存表單資料，避免向匿名者洩漏檔案存在
2. `email_norm` 或 `phone_norm` 命中既有人才 → 確認入庫時自動改為「**更新既有人才**」：只補既有資料的空欄、技能做合併不覆蓋（回應 `created=false`）；公開職涯站送出時亦依此合併
3. `platform_code`（平台履歷代碼）與 `dedup_hash`（姓名＋出生年）欄位已預留，**比對邏輯尚未啟用**（規劃：命中時列出候選，由 HR 決定合併或新建）

**處理策略**：校對介面確認入庫後以「已建立人才／已更新人才」回饋結果；同一人才可掛多份原始履歷檔（依上傳時間排序保存），聯繫與留言紀錄集中在人才主檔。

## 6. 信心分數與人工校對

- **逐欄位信心**：依規則命中方式給分（標籤精準命中高分、regex 命中次之、啟發式猜測低分）。
- **整體信心** = 有抽到值的欄位信心平均（不除以全欄位數，避免懲罰「欄位少但每欄都準」的履歷）。
- 解析狀態：版型可辨識、姓名與聯絡方式（Email 或電話）齊備、且 `overall >= 0.55` → 標記 `parsed`（可入庫）；否則 `needs_review` 進**校對佇列**。OCR 抽取的欄位一律信心 ×0.78 並強制 `needs_review`；`source_review_required`（來源待確認）也會擋住確認入庫。
- **HR 上傳的履歷一律由人工按「確認並寫入人才庫」才入庫**，系統不自動建檔；公開職涯站例外——送出即建檔，解析結果僅供 HR 後續校對。
- 校對介面：解析佇列選檔後，右側欄位表單搭配唯讀「解析原文」對照；低信心欄位標示提醒；校對修改過的欄位信心記為 1.0。已確認（`confirmed`）的履歷不可再編輯或重解析（回 409）。
- 入庫後人才詳情頁仍可回看原始 PDF（內嵌預覽）並直接修改人才欄位。

## 7. LLM 輔助解析（選配，目前未實作）

自由格式履歷（generic adapter）規則法準確率有限，未來可啟用 LLM 結構化抽取提升品質（現行解析管線完全不經 LLM）：

| 事項 | 做法 |
|---|---|
| 抽取方式 | Claude API + JSON Schema 強制結構化輸出，欄位同 `parsed_payload` |
| 個資保護 | **先以本地 regex 抽出並遮罩** Email/電話/身分證字號再送出（聯絡資訊本地已取得，不需 LLM）；啟用前完成個資影響評估並記錄於 docs/08 |
| 成本量級 | 每份履歷約 NT$0.3–2（依模型），僅對 generic 格式啟用，104/1111 固定版型走規則即可 |
| 替代方案 | 地端開源模型（需 GPU 主機）——資料不出內網，成本換硬體 |

## 8. 匯入操作流程（現行介面）

1. **HR／相容管理員網頁上傳**：「新增人才」→「上傳履歷」→ 拖放多檔（PDF/DOC/DOCX，單檔 10 MB）→ 逐檔顯示狀態（等待上傳／上傳中／等待解析／需人工確認／可入庫／重複檔案／失敗），批次完成顯示本批結果摘要
2. **主管送交**：主管在「送交履歷並指派職缺」先選定本部門職缺再上傳；看不到解析佇列與校對區，HR 校對入庫後自動建立該職缺的應徵紀錄
3. **公開職涯站**：求職者勾選個資告知同意後送出表單＋履歷 → **送出即建檔**（來源 `career_site`）；同步解析失敗時檔案保留在佇列（`pending`）供 HR 重試
4. **校對**：「解析佇列」只列尚未入庫的檔案（側欄徽章顯示待校對數）→ 選檔 → 必要時先做「來源確認」→ 修正欄位 →「確認並寫入人才庫」→ 到人才庫查看
5. **錯誤處理**：失敗／需確認的檔案留在佇列並附原因（無文字層且 OCR 失敗、舊版 .doc、版型未知等），可按「重新解析」或改走「手動填寫」建檔；格式不符（415）、超過大小（413）與掃毒攔下（422/503）在上傳當下即被拒絕，不會進入佇列

## 9. 解析器品質保證

- 樣本庫位於 `backend/tests/fixtures/resumes/`（附 `CALIBRATION.md` 操作準則）：目前為**去識別合成樣本**（p104 / p1111 / generic / 未知版型各一），不含任何真實個資；接入真實樣本前必須先去識別化，且不得將原始履歷提交進 Git
- Golden 斷言寫在 `backend/tests/test_parser_calibration.py`：每份樣本核對預期 payload（欄位級），版型改版時 bump 對應 adapter 的 `VERSION` 並通過全部 golden tests 才能發布
- 擴充目標（未達成）：104、1111 各版本 ≥ 10 份＋自由格式 20 份；固定版型必填欄位準確率 ≥ 95%、整體 ≥ 90%
- 已知不保證範圍見 `CALIBRATION.md`（加密 PDF、複雜表格、年資語意推論等）；不符已知平台簽章的 p104/p1111 檔案保留可抽取欄位但一律 `needs_review`
- 線上監控（規劃中）：週報「自動解析成功率 / 校對率 / 失敗率」，校對率突升 = 平台可能改版的警訊
