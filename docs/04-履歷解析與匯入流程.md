# 04. 履歷解析與匯入流程

**文件版本**：v1.0（2026-07-13）

> 文件定位：保存履歷合法取得、解析、OCR、校對與去重的流程基準；實際支援欄位、掃描政策與操作指令以程式、OpenAPI 及 [10-系統元件與資料庫使用手冊](10-系統元件與資料庫使用手冊.md) 為準。

## 1. 履歷的合法取得方式（前提）

| 來源 | 方式 | 說明 |
|---|---|---|
| 104 人力銀行 | 企業會員後台**手動下載**應徵者履歷 PDF / 主動開發下載 | 平台會員條款允許的正常使用 |
| 1111 人力銀行 | 同上 | |
| 求職者直接投遞 | Email 附件、紙本掃描 | |
| 內部推薦 | 推薦人轉交檔案 | 記錄推薦人於 `source_note` |

### 為什麼不做自動登入爬取？

1. **平台條款**：104 / 1111 會員條款禁止自動化程式抓取，違者企業帳號可能被停權——招募主要管道中斷的代價遠大於省下的下載時間。
2. **個資法風險**：以爬蟲繞過平台機制取得個資，蒐集手段的適法性有疑慮。
3. **技術成本**：反爬蟲對抗（驗證碼、行為偵測）維護成本高且不穩定。

### 替代方案：監控資料夾（自動化程度幾乎等同爬蟲）

HR 在 104/1111 後台批次下載履歷到約定資料夾（如 `\\NAS\resume_inbox\104\`、`\resume_inbox\1111\`），
Watcher 每 30 秒掃描：發現新檔 → 排入解析佇列 → 成功移至 `processed/`、失敗移至 `failed/` 並通知。
**HR 唯一的手動步驟只剩「在平台按下載」**，之後全自動。

> 未來若採購 104 企業方案的 API 服務，可增設 `Api104Source` 介接層，架構已預留（來源與解析器解耦）。

## 2. 支援的輸入格式

| 格式 | 解析器 | 說明 |
|---|---|---|
| 104 履歷 PDF（文字層） | `Parser104` | 固定版型，規則解析，目標欄位準確率 ≥ 95% |
| 1111 履歷 PDF（文字層） | `Parser1111` | 同上 |
| 一般 PDF / Word（.docx） | `GenericParser` | 自由格式，準確率較低，低信心進校對 |
| 掃描影像 PDF | （Phase 2）OCR 前置 | MVP 先標記 `needs_review` 走人工 |
| 批次 ZIP | 解壓後逐檔分派 | |

## 3. 解析管線（Pipeline）

```
上傳/Watcher → 佇列 → ①版型偵測 → ②文字抽取 → ③區塊切分 → ④欄位抽取
             → ⑤正規化驗證 → ⑥技能正規化 → ⑦去重比對 → ⑧信心計分 → 入庫 or 校對
```

| 步驟 | 做法 |
|---|---|
| ① 版型偵測 | 首頁文字特徵（「104人力銀行」字樣、版面指紋）判定 p104 / p1111 / generic |
| ② 文字抽取 | `pdfplumber` 取出帶座標的文字（word-level）；.docx 用 `python-docx` |
| ③ 區塊切分 | 以段落標題錨點切分：基本資料／求職條件／工作經歷／教育背景／語文能力／技能專長／證照／自傳 |
| ④ 欄位抽取 | 固定版型：鍵值對 + 表格座標定位；自由格式：regex（電話/Email/日期）+ 關鍵字啟發式 |
| ⑤ 正規化驗證 | Email regex、台灣手機 `09\d{8}`、**民國年→西元年**、期間「2021/3～至今」→ start/end_ym、薪資「4萬5～5萬」→ 45000–50000、年齡→出生年 |
| ⑥ 技能正規化 | 抽出的技能字串過 `skills.aliases` 字典對映到標準技能 ID；對不到的存為待審新技能 |
| ⑦ 去重比對 | 見 §5 |
| ⑧ 信心計分 | 見 §6 |

## 5. 去重（Deduplication）

**比對鍵優先序**：

1. `file_hash` 相同 → 同一檔案，直接標 `duplicated` 跳過
2. `platform_code` 相同（同平台履歷代碼）→ 同一人，**更新版本**
3. `email_norm` 或 `phone_norm` 命中既有人才 → 高度疑似同一人
4. `dedup_hash`（姓名+出生年）命中 → 中度疑似，列出候選

**處理策略**：命中 2/3 → 解析結果以「更新既有人才」呈現（新舊值並列，校對者確認）；
命中 4 → 校對介面顯示「疑似重複」黃色警示與比對卡，由 HR 決定合併或新建。
合併時保留兩份原始履歷檔（版本化），欄位取較新值，聯繫紀錄合併。

## 6. 信心分數與人工校對

- **逐欄位信心**：規則命中方式給分（表格精準定位 0.95+／regex 命中 0.8／啟發式猜測 0.5）＋驗證器通過與否。
- **整體信心** = 必填欄位（姓名/聯絡方式/最近經歷）信心加權平均。
- `overall >= 0.85`（可調）→ 自動入庫；否則進**校對佇列**。
- 校對介面：左側 PDF 原檔預覽、右側欄位表單，低信心欄位黃色標示，逐欄「跳至原文位置」。校對後按「確認入庫」。
- 即使自動入庫，人才詳情頁仍可隨時回看 `parsed_payload` 與原始 PDF 修正。

## 7. LLM 輔助解析（選配，預設關閉）

自由格式履歷（GenericParser）規則法準確率有限，可啟用 LLM 結構化抽取提升品質：

| 事項 | 做法 |
|---|---|
| 抽取方式 | Claude API + JSON Schema 強制結構化輸出，欄位同 `parsed_payload` |
| 個資保護 | **先以本地 regex 抽出並遮罩** Email/電話/身分證字號再送出（聯絡資訊本地已取得，不需 LLM）；啟用前完成個資影響評估並記錄於 docs/08 |
| 成本量級 | 每份履歷約 NT$0.3–2（依模型），僅對 generic 格式啟用，104/1111 固定版型走規則即可 |
| 替代方案 | 地端開源模型（需 GPU 主機）——資料不出內網，成本換硬體 |

## 8. 匯入操作流程（HR 視角）

1. **網頁上傳**：人才庫 →「匯入履歷」→ 拖曳多檔或 ZIP → 即時顯示解析進度條
2. **監控資料夾**：從 104/1111 下載到 `resume_inbox\104\` → 系統自動處理 → 站內通知「本批 28 份完成、2 份待校對」
3. **校對**：Dashboard 待校對佇列 → 逐份確認 → 入庫
4. **錯誤處理**：解析失敗檔案列於「失敗清單」附原因（加密 PDF／掃描檔／版型未知），可下載原檔改走手動建檔

## 9. 解析器品質保證

- `tests/samples/` 維護**去識別化**樣本庫（104、1111 各版本 ≥ 10 份 + 自由格式 20 份）
- 每份樣本附「標準答案 JSON」（golden set），CI 對每次修改跑欄位級準確率
- 準確率門檻：固定版型必填欄位 ≥ 95%、整體 ≥ 90%；低於門檻 CI 擋下
- 線上監控：週報「自動入庫率 / 校對率 / 失敗率」，校對率突升 = 平台可能改版的警訊
