# TalentHub 系統元件與資料庫使用手冊（第一版）

> 文件基準：2026-07-13 目前程式碼。本文以 SQLAlchemy models、Alembic migrations、
> FastAPI routes、兩套 Vue 前端與 Docker Compose 為準；規劃文件中尚未落地的功能不視為已完成。

## 1. 系統全貌

TalentHub 目前由五個主要部分組成：

| 元件 | 目錄／服務 | 用途 |
|---|---|---|
| 公開人才前端 | `career-frontend/` | 求職者查看公開職缺、應徵職缺或直接留下履歷；不需註冊登入 |
| HR 管理後台 | `frontend/` | HR、主管與管理員登入後管理人才、履歷、職缺、配對、報表與系統資料 |
| Backend API | `backend/` | 驗證、權限、資料驗證、履歷處理、配對、報表及資料庫存取 |
| PostgreSQL | Compose 的 `postgres` | 正式資料庫，保存結構化人才、職缺、流程、權限及稽核資料 |
| 履歷檔案儲存 | Local volume 或 S3／MinIO | 保存 PDF、DOC、DOCX 原檔；DB 只存 key、hash、大小及解析結果，不存檔案 binary |

主要資料流如下：

```text
求職者 ─→ 公開人才前端 ─→ /api/v1/public/* ─┐
                                               ├─→ Backend ─→ PostgreSQL
HR／主管 ─→ HR 後台 ─→ Bearer JWT API ────────┤              └→ 履歷檔案儲存
Admin ───→ HR 後台 Admin 頁 ─→ /admin/* ──────┘
```

實際核心流程：

1. HR 建立並核准職缺；核准、招募中或面試中的職缺可由公開 API 讀取。
2. 求職者應徵時會建立或連結 `candidates` 與 `job_applications`；若有附履歷，Backend 另外驗證檔案、
   寫入檔案儲存並建立 `resume_files`。
3. 沒有指定職缺時可只用姓名、至少一種聯絡方式與同意加入人才庫；未附履歷會直接建立人才主檔，
   有附履歷則先進解析與 HR 校對流程。
4. HR 也可將合法取得的 104、1111 或一般履歷批次上傳，校對解析欄位後確認入庫。
5. 針對職缺重新計算配對時，結果保存到 `match_results`，不是只存在瀏覽器。
6. 報表 API 直接聚合 DB 的人才、投遞、職缺與技能資料，不使用前端 mock 數字。

### 1.1 為什麼前後端使用不同技術？

可以把 TalentHub 想成一間餐廳：

- **前端是用餐區與服務人員**：負責讓使用者看得懂、填得快、立即知道哪裡需要修正。
- **Backend 是廚房**：負責驗證資料、解析履歷、計算配對分數，以及決定資料可以如何被使用。
- **資料庫是倉庫與帳本**：負責長期、正確地保存人才、職缺、權限與操作紀錄。
- **履歷儲存是文件庫**：保存 PDF、DOC、DOCX 原始檔，資料庫只記錄檔案位置與解析結果。

各層工作不同，因此選擇最適合該工作的工具，比強迫全部使用同一種語言更容易維護。

### 1.2 技術選擇對照表

| 系統層 | 使用技術 | 主要負責工作 | 選擇原因 |
|---|---|---|---|
| 公開人才前端 | Vue 3＋TypeScript | 職缺瀏覽、人才表單、下拉選單、履歷上傳、錯誤提示 | Vue 適合互動表單與元件化畫面；TypeScript 可在開發階段找出欄位型別錯誤 |
| HR 管理後台 | Vue 3＋TypeScript | 人才列表、搜尋篩選、履歷校對、職缺、配對、報表及系統管理 | 管理後台有大量重複的表格、按鈕與表單，元件可以重複使用並保持操作一致 |
| Backend API | Python＋FastAPI | 權限、資料驗證、履歷解析、OCR、去重、配對及報表 | Python 有成熟的文件解析、OCR、資料處理與 AI 工具；FastAPI 可快速建立有型別驗證及 API 文件的服務 |
| 正式資料庫 | PostgreSQL＋SQL | 保存人才、經歷、技能、履歷、職缺、配對、帳號及稽核資料 | 支援交易、外鍵、索引、複雜查詢、多人同時操作及正式備份還原 |
| 本機測試資料庫 | SQLite | 單元測試及快速本機驗證 | 不需另外安裝資料庫服務；啟動快速，但不作為正式多人環境 |

### 1.3 從畫面到資料庫的架構圖

```text
┌──────────────────────── 使用者看到的畫面 ────────────────────────┐
│  求職者 → 公開人才前端（Vue＋TypeScript）                       │
│  HR／主管／Admin → HR 管理後台（Vue＋TypeScript）               │
└────────────────────────────┬───────────────────────────────────┘
                             │ HTTPS／JSON／履歷檔案
                             ▼
┌──────────────────────── 系統處理中心 ───────────────────────────┐
│  Backend API（Python＋FastAPI）                                 │
│  驗證身分與權限 → 檢查欄位 → 解析履歷／OCR → 去重／配對／報表   │
└───────────────────────┬───────────────────┬────────────────────┘
                        │ 結構化資料         │ PDF／DOC／DOCX 原檔
                        ▼                    ▼
              ┌──────────────────┐  ┌─────────────────────────┐
              │ PostgreSQL       │  │ Local／S3／MinIO        │
              │ 人才、職缺、權限 │  │ 履歷原始檔案            │
              │ 配對、稽核紀錄   │  │ 隔離區與惡意檔案掃描    │
              └──────────────────┘  └─────────────────────────┘
```

### 1.4 各項選擇的白話原因

**前端使用 Vue 3＋TypeScript**

- Vue 適合人才表單、資料表格、篩選器、彈出視窗等互動畫面，並能將畫面拆成可重複使用的元件。
- 公開人才網站與 HR 後台都採用相同前端技術，工程師不必維護兩套不同的畫面框架。
- TypeScript 會檢查資料型別。例如 API 回傳的人才缺少 `name`，或年資被誤傳成文字時，開發階段就較容易發現。

**Backend 使用 Python＋FastAPI**

- 本系統不只有資料新增與修改，還需要處理 104、1111、一般履歷、PDF、DOCX、OCR、技能正規化及配對計分。
- Python 在文件解析、OCR、資料清理與未來 AI 輔助解析方面有成熟工具，適合本專案的核心工作。
- FastAPI 可驗證前端送來的資料、自動產生 OpenAPI／Swagger 文件，並容易整合 JWT、RBAC、檔案上傳及自動測試。

**正式資料庫使用 PostgreSQL**

- 一位人才可能有多筆學歷、經歷、技能、履歷、應徵與配對結果，屬於需要明確關聯的資料。
- PostgreSQL 的交易可避免只寫入一半資料；外鍵可避免履歷連到不存在的人才；索引則能提升大量人才篩選速度。
- PostgreSQL 適合多人同時操作，也具備正式環境所需的備份、還原與權限能力。

**為什麼不全部使用同一種語言？**

全部使用 JavaScript／TypeScript 可以減少語言種類，但會放棄 Python 在履歷解析、OCR 與資料處理上的優勢。
目前的分工讓 Vue＋TypeScript 專注於畫面與操作、Python＋FastAPI 專注於規則與文件處理、PostgreSQL 專注於可靠保存資料。
不同層透過清楚的 HTTP API 規格溝通，因此仍能分開測試、替換與維護。

## 2. 資料庫選型、連線與 migration

### 2.1 PostgreSQL 與 SQLite 的定位

| 項目 | PostgreSQL 16 | SQLite |
|---|---|---|
| 定位 | 正式部署與整合驗證的資料庫 | 單元測試、快速本機檢查 |
| 多使用者／併發 | 適合 | 不適合作為正式多人系統 |
| 型別 | 真正 BIGINT、時區 timestamp、JSON | 測試時有型別簡化與反射差異 |
| 備份 | `pg_dump`／`pg_restore`、託管快照 | 複製單一 DB 檔案，但不能代表 PostgreSQL 備份測試 |
| 建議 | 正式環境唯一選擇 | 不可用來宣稱 PostgreSQL migration 已驗證 |

SQLAlchemy 的主鍵型別在 PostgreSQL 使用 BIGINT，在 SQLite 測試時切換為 INTEGER，讓測試資料庫可以自增。

### 2.2 連線設定

Backend 從 `DATABASE_URL` 讀取連線字串。Docker Compose 範例使用服務名稱 `postgres`：

```text
postgresql+psycopg://<db_user>:<db_password>@postgres:5432/<db_name>
```

若 Backend 直接在 Windows 主機執行，而 PostgreSQL 對外開在本機，host 通常要改成 `localhost`。
帳號、密碼與 `AUTH_SECRET_KEY` 應放在未提交版本控制的 `.env`，不得沿用範例值至正式環境。

### 2.3 Alembic migration

目前 migration chain 的 head 是 `f73a9c0d4b11`。實際部署一律執行 Alembic，不要用
`Base.metadata.create_all()` 取代正式 migration：

```powershell
Set-Location backend
python -m alembic heads
python -m alembic current
python -m alembic upgrade head
```

Docker Compose 的 `migrate` service 會等 PostgreSQL healthcheck 通過後執行 `alembic upgrade head`；
只有 migration 成功，Backend 才會啟動。

### 2.4 備份基本原則

PostgreSQL 邏輯備份範例（請替換 placeholder，且將輸出保存到受控備份位置）：

```powershell
docker compose -f deploy/docker-compose.yml exec -T postgres pg_dump `
  -U <db_user> -d <db_name> -Fc > talenthub.dump
```

還原時應先建立空白的還原用資料庫，先在非正式環境演練：

```powershell
pg_restore -d <empty_restore_database_url> talenthub.dump
```

注意：DB 備份不包含履歷原檔。`resume_data` volume、公司 NAS 或 S3／MinIO bucket 必須另外備份，
並定期抽驗「DB 的 `storage_key` 能找到原檔」。正式環境也應設定備份加密、保存期限、異地副本與還原演練。

## 3. 實際資料表清單

除 Alembic 自己維護的 `alembic_version` 外，目前應用程式共有 16 張資料表。

### 3.1 組織與帳號

| 資料表 | 用途與主要欄位 | 關聯 | 資料來源 |
|---|---|---|---|
| `departments` | 部門階層；`name`、`parent_id`、`is_active` | `parent_id` 自關聯；被 users、jobs、audit 引用 | Admin 後台建立／修改 |
| `users` | 登入帳號；`username`、`email`、`password_hash`、`display_name`、`role`、`department_id`、`is_active` | 所屬 department；被 refresh token、audit 等引用 | 首位管理員 bootstrap；其後由 Admin 管理 |
| `refresh_tokens` | Refresh token 輪替與撤銷；只存 `jti_hash`、到期與撤銷時間，不存明文 token | `user_id → users.id`，使用者刪除時 cascade | 登入及 refresh API 自動建立 |

`users.role` 目前只允許 `admin`、`hr`、`manager`。

### 3.2 人才資料

| 資料表 | 用途與主要欄位 | 關聯 | 資料來源 |
|---|---|---|---|
| `candidates` | 人才主檔；代碼、姓名、正規化 Email／電話、城市、學歷、年資、現職、期望條件、來源、狀態、同意、黑名單、保存期限、軟刪除時間 | owner 可連 users；一對多教育、經歷、技能、活動、履歷、投遞、配對 | 公開投遞、HR 手動建立、履歷確認入庫 |
| `candidate_educations` | 學校、主修、學位、起訖年月、畢業狀態與順序 | `candidate_id → candidates.id`，刪除人才時 cascade | Model 與 DB 已具備；目前主要 UI 尚未提供完整逐筆編輯 |
| `candidate_experiences` | 公司、職稱、產業、起訖年月、年資、說明與順序 | `candidate_id → candidates.id`，刪除人才時 cascade | Model 與 DB 已具備；目前主要 UI 尚未提供完整逐筆編輯 |
| `candidate_skills` | 可搜尋的正規化技能；`skill`、`skill_norm` | 每位人才的 `skill_norm` 不可重複 | 履歷確認入庫時由解析／校對技能建立 |
| `candidate_activities` | 聯繫、備註、面談等歷程；`type`、`content`、`happened_at` | `candidate_id → candidates.id`；`user_id → users.id` | HR 後台新增活動紀錄 |

`candidates.deleted_at` 是軟刪除欄位；一般人才列表與報表會排除已軟刪除人才。履歷解析當下的 JSON
snapshot 在 `resume_files.parsed_payload`，可搜尋的正式技能則以 `candidate_skills` 為準。

### 3.3 招募、履歷與配對

| 資料表 | 用途與主要欄位 | 關聯 | 資料來源 |
|---|---|---|---|
| `job_requisitions` | 職缺需求；單號、部門、需求人數、地點、薪資、年資／學歷條件、JD、技能 JSON、權重、狀態及發布／補齊／關閉時間 | department、requested/approved user；一對多 applications、matches | HR 後台建立、編輯、核准 |
| `resume_files` | 履歷原檔 metadata 與解析結果；`storage_key`、檔名、SHA-256 hash、大小、MIME、來源平台、解析狀態、文字、payload、信心分數 | 可連 `candidate_id`；被 application 引用 | 公開人才前端或 HR 批次上傳 |
| `job_applications` | 人才對職缺的投遞；履歷、cover letter、作品連結、流程狀態、來源 | requisition、candidate 必填；resume 可空；同一人才對同一職缺不可重複 | 公開應徵 API或結構化 client |
| `match_results` | 可重算的職缺人才配對；門檻、總分、分項 JSON、排名、流程狀態、主管理由與計算時間 | requisition、candidate；feedback user | HR 後台「重新計算配對」及後續狀態／主管回饋 |

`resume_files` 不保存 binary；原檔位於 Local volume 或 S3 相容儲存。相同 `file_hash` 會用於阻擋重複履歷。

### 3.4 管理與稽核

| 資料表 | 用途與主要欄位 | 關聯 | 資料來源 |
|---|---|---|---|
| `skill_catalog` | 系統技能字典；名稱、正規化名稱、啟用狀態 | 目前是獨立管理 catalog，尚未直接 FK 到 candidate_skills | Admin 後台 |
| `tags` | 分類標籤字典；名稱、category、啟用狀態 | 目前尚無 candidate-tag 關聯表 | Admin 後台 |
| `system_settings` | JSON／字串等系統設定；key、value、說明、是否秘密 | 無外鍵；秘密值 API 不回傳明文 | Admin 後台 |
| `audit_logs` | 登入、管理異動與 PII 讀取稽核；actor、action、resource、department、details、IP、User-Agent、時間 | actor user 與 department 可為空 | Auth、Admin 操作，以及人才詳情讀取 dependency |

## 4. 公開人才前端

### 4.1 是什麼

`career-frontend/` 是提供求職者使用的公開網站，不是 HR 後台。現在可：

- 瀏覽、搜尋公開職缺及查看職缺內容；
- 針對職缺填寫基本資料，履歷可選填；
- 沒有合適職缺時用下拉選單快速提供地點、職務、年資與專長，直接加入人才庫；
- 顯示送出成功與參考編號。

不需註冊或登入。姓名、Email／手機至少一項、資料使用同意為必要資料，其餘欄位與履歷均可選填。
若上傳履歷，接受 PDF、DOC、DOCX 且限制 10 MB；Backend 仍會再次驗證副檔名、MIME、檔案內容、
大小與安全掃描政策，不能只依賴瀏覽器檢查。

### 4.2 本機啟動

先啟動 Backend，再開新終端機：

```powershell
Set-Location career-frontend
$env:VITE_API_PROXY_TARGET="http://127.0.0.1:8000"
npm ci
npm run dev
```

網址預設為 <http://localhost:5174>。目前 `career-frontend/vite.config.ts` 的 proxy 預設 target 是 port 8010，
而標準 Backend 指令使用 8000，因此本機同時開發時應明確設定上述環境變數。

## 5. Backend API

### 5.1 是什麼與啟動方式

Backend 是 FastAPI 應用，所有正式資料寫入、驗證、權限與商業規則都在這一層處理。

```powershell
python -m pip install -e "backend[dev]"
Set-Location backend
$env:DATABASE_URL="postgresql+psycopg://<user>:<password>@localhost:5432/<database>"
python -m alembic upgrade head
python -m uvicorn app.main:app --reload --port 8000
```

- OpenAPI：<http://localhost:8000/docs>
- Health：<http://localhost:8000/api/v1/health>
- API base：`/api/v1`

### 5.2 API 分類

| 路由群組 | 主要用途 | 是否需 Token |
|---|---|---|
| `/health` | 服務存活檢查 | 否 |
| `/public/jobs*` | 公開職缺列表／詳情 | 否 |
| `/public/applications`、`/public/talent-pool` | multipart 應徵／加入人才庫；履歷檔為選填 | 否 |
| `/public/applications/json` | 結構化 client 投遞端點 | 否；正式公開前應依風險決定是否保留 |
| `/auth/login`、`/auth/refresh` | 登入與 refresh token 輪替 | 否 |
| `/auth/me` | 目前登入者 | 是 |
| `/candidates*` | 人才 CRUD、活動、軟刪除 | 是 |
| `/resumes*` | 批次上傳、列表、詳情、校對、重解析、確認入庫 | 是 |
| `/requisitions*` | 職缺 CRUD、核准 | 是；非 Admin 受部門限制 |
| `/requisitions/{id}/matches`、`/matches*` | 配對列表、重算、狀態、主管回饋 | 是；受職缺部門限制 |
| `/reports/funnel`、`time-to-fill`、`sources`、`talent-pool` | 真實 DB 聚合報表 | 是；非 Admin 自動套用所屬部門 |
| `/admin/*` | 使用者、部門、技能、標籤、設定、稽核 | 僅 Admin |

Access token 由 `Authorization: Bearer <token>` 傳入；refresh token 會輪替，舊 token 不能重複使用。
Backend 沒有公開註冊 API。首次管理員需透過 `.env` 的三個 `BOOTSTRAP_ADMIN_*` 設定建立，成功後應立即移除。

目前角色邊界要特別注意：Admin 可跨部門；HR 與 Manager 在職缺、配對、報表會受部門限制；
除 Admin API 外，現有程式尚未進一步區分 HR 與 Manager 的寫入能力，因此兩者目前都能呼叫人才、履歷等受保護 API。
這是後續權限細分需補強的項目。

## 6. HR 管理後台

### 6.1 是什麼

`frontend/` 是瀏覽器中的內部管理系統。它雖然也是「前端程式」，產品角色上屬於 HR 後台。
登入 token 保存在 browser session storage，API 遇到 401 時會嘗試 refresh；登出會清除 session token。

### 6.2 現有頁面

| 頁面 | 現有功能 |
|---|---|

## 7. Local 與 Docker 快速操作

### 7.1 Docker Compose（建議）

```powershell
Copy-Item .env.example .env
# 編輯 .env：更換 DB 密碼、至少 32 bytes 的 AUTH_SECRET_KEY，並設定首次 Admin bootstrap
docker compose -f deploy/docker-compose.yml up --build -d
docker compose -f deploy/docker-compose.yml ps
```

| 服務 | URL／用途 |
|---|---|
| HR 後台 | <http://localhost:8080> |
| 公開人才前端 | <http://localhost:8081> |
| Backend／OpenAPI | <http://localhost:8000/docs> |
| PostgreSQL | 只供 Compose 內部服務使用；主 compose 未映射 host port |
| Redis | 已啟動，但目前核心同步流程沒有 Celery worker service |

主 Compose 預設使用 Local resume volume。若要測試 MinIO 與 ClamAV，可疊加 storage compose，並同步把 `.env`
的 provider／scanner 改成對應設定：

```powershell
docker compose -f deploy/docker-compose.yml -f deploy/compose.storage.yml up --build -d
```

`compose.storage.yml` 的預設 access key／secret 只適合本機測試，正式環境必須更換且不可提交。

### 7.2 本機非 Docker

1. 自行準備 PostgreSQL，建立 DB 與最小權限帳號。
2. 設定 host 為 `localhost` 的 `DATABASE_URL`。
3. 依序啟動 Backend、HR 前端及公開前端。
4. 若只需快速單元測試，可暫用 `sqlite:///...`，但正式驗收仍需 PostgreSQL CI／環境。

## 8. 常見驗證指令

Backend：

```powershell
Set-Location backend
python -m alembic heads
python -m alembic upgrade head
python scripts/postgres_schema_smoke.py
python -m pytest -q
python -m ruff check app tests scripts
```

HR 後台：

```powershell
Set-Location frontend
npm run typecheck
npm run build
```

公開人才前端：

```powershell
Set-Location career-frontend
npm run typecheck
npm run build
```

Docker：

```powershell
docker compose -f deploy/docker-compose.yml config
docker compose -f deploy/docker-compose.yml ps
docker compose -f deploy/docker-compose.yml logs migrate
docker compose -f deploy/docker-compose.yml exec backend python scripts/postgres_schema_smoke.py
```

`postgres_schema_smoke.py` 必須連到 PostgreSQL；用 SQLite 執行會刻意失敗，以避免把 SQLite 結果誤當正式 DB 驗證。
