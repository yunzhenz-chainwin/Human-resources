# 11. 人才職缺媒合試行方案

**更新日**：2026-08-27

**定位**：先以可解釋、可稽核的 skills-first 規則做 shadow pilot，不讓系統自動做最終錄用決策。

## 可直接採用的業界做法

| 做法 | 本平台狀態 | 落地方式 |
|---|---|---|
| 技能優先（skills-first） | 已有 | 必要技能權重高於學歷、公司名等背景代理訊號 |
| 必要條件／加分條件分流 | 已有 | required skills 作 gate；preferred skills 只加分 |
| 技能字典與同義詞 | 已擴充 | 同義詞表含中英對照、縮寫（JS、K8s、ML）與版本變體（react／react.js），並加保守模糊比對；下一階段可接 ESCO／O*NET 或公司內部 taxonomy |
| 關鍵字＋語意混合檢索 | 待 shadow test | 先保留現有結構化分數，再平行產生 embedding 分數，以 rank fusion 比較但不影響正式排序 |
| 可解釋命中證據 | 已有 | 顯示每項分數、命中技能、缺漏欄位與淘汰 gate |
| 招募人員／主管回饋 | 已有 | 面試、錄用、拒絕及原因保存於 match result；重新媒合只更新分數與 gate，不覆寫人工階段決定與例外覆核 |
| 以結果校準排序 | 已加評估入口 | 以媒合評估報表量測；至少累積 30 筆標記結果後才調權重，更多樣本後才評估 learning-to-rank |
| 公平性與人工覆核 | 基線 | 年齡、性別、照片、宗教、婚姻、身心狀況不得進入分數；最終決定由人員覆核 |

## 媒合引擎改進（本次）

沿用可解釋的 skills-first 規則，本次針對「同義詞太窄、硬門檻過嚴、職稱比對用字元相似度」三個誤判來源做修正，最終仍由人員覆核決策。

### 技能比對

- **同義詞表擴充**：涵蓋中英對照（機器學習 ↔ machine learning）、常見縮寫（JS→javascript、K8s→kubernetes、ML→machine learning）與版本／寫法變體（react.js／reactjs → react、node.js／nodejs → node.js）。
- **保守模糊比對**：僅在同義詞表未命中時啟用，且要求比對雙方的正規化（canonical）token 長度均 ≥ 5、字串相似度 ≥ 0.86 才視為同一技能，避免 Java 誤配 JavaScript 這類短字或近形誤判。

### 硬門檻軟化

- **可調 required 技能比例**：每張職缺新增 `required_skill_ratio`（0–1，預設 `1.0`）。`1.0` 維持「須具備全部 required 技能」；調低則命中比例達標即通過硬門檻，放行強度足夠的部分符合者。
- **地點門檻放寬**：由「須完全命中工作城市」改為「接受鄰近城市」，與地點軟分數採同一組相鄰城市判斷，標準一致。
- **near_miss 旗標**：`score_breakdown` 新增 `near_miss`，標示「只差一項硬條件、但整體分數仍高（≥ 60）」的 stretch 人選，讓 HR 看得到而非被直接淘汰。

### 職稱相關度

改用雙語 role-token 比對：先把職稱拆成正規化角色詞（資深、後端、工程師 → senior／backend／engineer），再比對重疊度，使「資深後端工程師」能對上「Backend Engineer」。僅在任一邊職稱無法辨識出角色詞時，才退回原本的字元級相似度。

## 平台試行方式

1. 選 1–2 個需求穩定、條件清楚的職缺。
2. HR 與主管先定義必要技能、可培養技能及真正必要的 gate。
3. 執行媒合但先採 shadow mode：系統排名不直接淘汰人才。
4. 每一筆面試／拒絕都填原因，避免只有分數沒有結果資料。
5. 使用 `GET /api/v1/requisitions/{id}/match-readiness` 查看：
   - 可媒合率與平均分數
   - 履歷資料完整度
   - 有效結果／回饋覆蓋率
   - 有標註結果時的 Precision@5
6. 有 30 筆以上有效結果後再調整權重；若語意 shadow score 確實改善 Top-K，再導入混合排序。

### 合成小樣本基準

目前另有 50 組「合成職缺 × 合成履歷」案例，讓 HR 與主管在看不到系統分數時獨立盲評，用來提早找出 gate 誤殺、排序偏差、技能同義詞缺口及資料不足。這是工程流程基準，不是錄取預測準確率，也不寫入正式人才、職缺或應徵資料。

建立資料、盲評步驟、指標及 API 詳見 [媒合小樣本基準：操作與指標說明](媒合小樣本基準_操作與指標說明.md)。策略與是否調權重的結論仍統一回寫本文件，避免 Runbook 與試行策略各自形成不同版本。

## 媒合評估報表

用來回答「媒合準不準」，資料來源為 `match_results` 的人工標記結果：`interview`／`offered`／`hired` 視為正向，`rejected_by_manager`／`withdrawn` 視為負向。指標包含：

- **Precision@K（K=5,10）**：前 K 名推薦中實際為正向的比例，檢視排序頭部品質。
- **Recall@K（K=5,10）**：抓出「被硬門檻誤殺、但其實是好人選」的漏網程度。
- **Gate 誤殺率**：被 gate 淘汰、事後卻獲正向結果的比例。
- **分數分桶校準**：各分數區間對應的實際正向率，檢查分數是否可信。
- **排名有效性**：名次越前是否確實對應越高的正向率。

需累積約 30 筆標記結果，指標才夠穩定、足以支撐自動調權重；未達門檻前僅供觀察。查詢入口見 API 規格書 `GET /reports/matching-evaluation`（HR／admin 可看全公司，主管限本部門）。

## 現階段結論

目前平台適合進行「可解釋規則基線」的內部 shadow pilot。尚不應直接宣稱為 AI 自動選才，也不應在沒有結果標註與公平性檢查前，啟用自動淘汰或自動錄用。

## 下一步（未做，需資料／決策）

- **learning-to-rank 權重校準**：累積足量標記結果後，用實際錄用資料回歸各項權重，取代人工設定。
- **語意 embeddings**：先以影子計分（shadow score）平行產生語意相似度，與現有結構化分數做 rank fusion 比較，確認改善 Top-K 後再導入正式排序。
- **技能抽取改善**：提升從履歷抽取技能的涵蓋率與正確率，減少因漏抽造成的誤判。
- **相關年資**：改以「與職缺相關的年資」而非總年資計分。
