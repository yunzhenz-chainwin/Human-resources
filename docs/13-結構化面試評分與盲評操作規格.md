# TalentHub 結構化面試評分與盲評操作規格

更新日期：2026-08-06

適用範圍：HR 初談、部門主管複試、面試紀錄 API、IT 後台稽核與後續報表

目前狀態：程式、後端自動測試、前端正式建置與本機 migration 已完成；正式發布仍須完成瀏覽器 UAT、PostgreSQL 演練及 PR／IT 簽核

## 1. 目的與不可妥協原則

本功能用結構化評分補強既有面試紀錄，讓每一題的證據、評分、未詢問原因及整體總評可追蹤。它不是自動錄取工具。

1. 每題採 **1–5 分**；分數評的是與職務相關的回答證據，不評年齡、性別、婚姻、健康、宗教、外貌或其他受保護特徵。
2. 面試完成時，每題必須在「1–5 分」與「未詢問原因」之間二擇一。
3. 回答文字 `response` 即使在完成時仍可空白，系統不得因未逐字記錄回答而阻止提交。
4. 草稿可以不完整；提交為 `completed` 後即鎖定，一般修改不得覆寫。
5. 重開必須走獨立 API、重新檢查角色與部門範圍並留下稽核紀錄。
6. HR 與主管在雙方完成前互相看不到評分結論，避免先看他人意見造成錨定偏誤。
7. 題目版本與面試紀錄永久綁定；重新產生題目只新增版本，不覆蓋舊紀錄。
8. `recommendation` 及分數都是建議，不得自動把應徵狀態改為錄取、淘汰或發 Offer。
9. 每次正式提交都要留下提交者、提交時間與修訂次數；重開必須填寫非空原因。

## 2. 角色與資料範圍

| 動作 | HR | 該部門主管 | 其他部門主管 | IT | 相容管理員 `admin` |
|---|---|---|---|---|---|
| 讀取應徵者面試紀錄 | 全公司招募範圍 | 僅自己部門實際應徵者 | 禁止 | 禁止讀取招募內容 | 保留全公司相容讀取權限 |
| 建立／修改 HR 階段 | 允許 | 禁止 | 禁止 | 禁止 | 禁止，並非面試作者 |
| 建立／修改主管階段 | 禁止 | 允許 | 禁止 | 禁止 | 禁止，並非面試作者 |
| 重開 HR 已完成紀錄 | 允許 | 禁止 | 禁止 | 禁止 | 禁止 |
| 重開主管已完成紀錄 | 禁止 | 允許 | 禁止 | 禁止 | 禁止 |
| HR 私人備註 | HR 可讀寫 | 永不顯示 | 永不顯示 | 永不顯示 | 永不顯示 |
| 維護系統問題、部署與監控 | 不讀取候選內容 | 不讀取系統機密 | 不適用 | 允許維運中繼資料 | 允許維運中繼資料 |

權限必須由後端強制執行，不能只靠前端隱藏按鈕。跨部門主管與 IT 讀取 API 應回 `403`；錯誤階段、IT 或相容管理員執行建立、修改、提交或重開也應回 `403`。相容 `admin` 的全域讀取是既有相容行為，日常維運應改用不含招募資料權限的 `it` 角色。

## 3. 評分欄位與 1–5 量表

### 3.1 每題欄位

| 欄位 | 用途 | 完成時規則 |
|---|---|---|
| `question` | 當時實際使用的題目快照 | 必須為非空文字 |
| `response` | 候選人回答摘要 | 可空；建議只記錄客觀證據 |
| `rating` | 1–5 分 | 與 `not_asked_reason` 二擇一 |
| `not_asked_reason` | 未詢問原因 | 去除前後空白後須為非空；與 `rating` 二擇一 |
| `notes` | 評分依據或追蹤事項 | 可空；盲評釋出前不給另一方看 |
| `trait`、`purpose`、`follow_up`、`source` | 題目脈絡與稽核資訊 | 沿用題目版本，不拿來自動決策 |

完成時的合法組合：

- 有詢問：`rating` 為 1–5；`not_asked_reason` 為空。`response` 可有可無。
- 未詢問：`rating` 為空；`not_asked_reason` 為非空文字。
- 兩者都空、兩者同時填、0 分、6 分或空白原因皆為 `422`。

### 3.2 統一量表

| 分數 | 定義 | 建議紀錄方式 |
|---:|---|---|
| 1 | 未呈現職務所需證據，或回答與題目無關 | 寫出缺少哪一項行為／結果，不貼人格標籤 |
| 2 | 只有片段證據，需大量提示才能說明 | 記錄仍待確認的具體缺口 |
| 3 | 達到此職務的基本期待 | 記錄符合條件的事例與範圍 |
| 4 | 證據清楚且高於基本期待 | 記錄可驗證的影響、複雜度或主動性 |
| 5 | 在高複雜度情境中持續展現卓越證據 | 必須寫出可驗證成果，避免只憑整體印象 |

同一職缺應先校準「3 分」的基準。不得把 1–5 分當成精密的心理測量，也不得跨職缺直接比較未校準的平均分。

### 3.3 未詢問原因

建議使用短而中性的原因，例如：

- 時間不足；
- 前題已取得足夠證據；
- 題目與本次職務不適用；
- 改由下一階段確認；
- 候選人無法理解題目，已改問等價題。

不要在原因欄寫「懷孕所以沒問」、「年紀太大無需再問」或健康、家庭等敏感資訊。`not_asked_reason` 是評估中繼資料，在盲評釋出前必須與分數一起遮罩。

## 4. 整體總評

面試提交為 `completed` 時，除逐題規則外，以下三項都必填：

| 欄位 | 規則 |
|---|---|
| `overall_rating` | 1–5；由面試官依全部職務證據做整體判斷，不要求等於逐題算術平均 |
| `recommendation` | `advance`、`hold`、`reject` 或 `offer` |
| `summary` | 去除前後空白後仍須為非空，說明主要證據、缺口與需追蹤事項 |

整體總評不得包含受保護特徵，也不得直接觸發應徵狀態。HR 與主管仍須依公司授權流程另行做錄取、淘汰或 Offer 決策。

## 5. 草稿、提交、鎖定與重開

### 5.1 草稿

- `planned`、`in_progress` 是可編輯狀態，可暫時沒有分數、未詢問原因、整體評分、建議或摘要。
- `cancelled`、`no_show` 不要求評分，且不視為完成盲評。
- 草稿可透過一般 `PATCH` 儲存；每次更新仍須驗證角色、部門範圍及 HR 私人備註權限。

### 5.2 提交

- 建立時直接使用 `completed`，或把草稿 `PATCH` 成 `completed`，都必須套用相同的完整驗證。
- 更新提交時，後端要把資料庫現況與本次局部更新合併後再驗證，不能只檢查 PATCH 中出現的欄位。
- 合法提交後回傳 `completed`，並留下建立／更新稽核紀錄。

### 5.3 完成鎖定

- `completed` 紀錄的任何一般 `PATCH` 都回 `409 Conflict`，包括只改摘要或直接把狀態改回 `in_progress`。
- 鎖定必須在後端執行；即使前端按鈕被繞過，資料仍不能被改寫。
- `question_plan_id` 與 `question_plan_version` 從建立起即不可透過 PATCH 修改。

### 5.4 重開

重開端點：

```http
POST /api/v1/applications/{application_id}/interview-records/{record_id}/reopen
```

預期行為：

1. Request body 必須為 `{ "reason": "非空的重開理由" }`；缺少、空字串或只有空白回 `422`。
2. 僅目前為 `completed` 的紀錄可重開；重複重開回 `409`。
3. 重新套用 application、部門與 stage owner 權限；HR 不能重開主管紀錄，主管不能重開 HR 紀錄。
4. 狀態改為 `in_progress`，保留原題目、分數、摘要、建議、整體評分及原題目版本，讓使用者修正後重新提交。
5. 把去除前後空白的理由存入 `last_reopen_reason`；此欄只用來說明修訂原因，不得填候選人個資或完整回答。
6. 留下獨立 `application.interview_record.reopen` 稽核事件，包含紀錄、應徵、階段、舊／新狀態、修訂次數、重開理由、操作者、部門、時間、IP 與 user agent；稽核 details 不應複製完整回答或私人備註。
7. 任一方重開後，雙方盲評立即恢復遮罩，直到兩個最新階段紀錄再次完成。

### 5.5 提交中繼資料與修訂次數

| 情境 | `revision_number` | `submitted_at`／`submitted_by_*` | `last_reopen_reason` |
|---|---:|---|---|
| 新建草稿 | 0 | `null` | `null` |
| 首次提交完成 | 1 | 記錄本次提交時間與操作者 | `null` |
| 第一次重開 | 維持 1 | 保留前次提交中繼資料 | 記錄非空重開理由 |
| 修正後再次提交 | 2 | 更新為本次提交時間與操作者 | 保留最近一次重開理由 |
| 再重開、再提交 | 每次提交加 1 | 每次提交更新 | 保留最近一次重開理由 |

`submitted_at` 及 `revision_number` 可作為流程狀態提示；在盲評釋出前，另一方的 `submitted_by_id`、`submitted_by_name` 與 `last_reopen_reason` 必須遮罩。擁有該 stage 的面試官可看自己的完整中繼資料。

## 6. 雙方盲評與釋出規則

### 6.1 提交前

- 面試官隨時可看自己的評分。
- HR 與主管可以共享題目及候選人的 `response`，便於接續追問。
- 另一方的 `rating`、`not_asked_reason`、`notes`、`summary`、`recommendation`、`overall_rating`、`submitted_by_id`、`submitted_by_name` 與 `last_reopen_reason` 必須回傳 `null`，且 `evaluation_revealed=false`。
- HR `private_notes` 永不對主管顯示，不因雙方完成而釋出。

共享的 `response` 只能寫候選人陳述或客觀證據。如果把「我覺得很差／一定錄取」寫進回答欄，仍會破壞盲評，這屬操作與 UI 提示的驗收項目。

### 6.2 釋出

只有 HR 與主管各自最新一筆面試紀錄都為 `completed` 時，才對彼此釋出評分欄位。`cancelled`、`no_show`、`planned`、`in_progress` 都不構成完成配對。

若任一方重開，釋出條件失效並立即重新遮罩。已取得資料的瀏覽器不得繼續顯示舊快取；前端重開成功後應重新抓取雙方紀錄。

### 6.3 職缺層級的揭露開關

盲評並非全系統固定，而是由職缺欄位 `blind_review_enabled` 決定；本章 6.1／6.2 的遮罩規則適用於採盲評（`true`）的職缺。

- 預設為盲評。設成 `false` 代表該職缺的 HR 與主管即時互看評分，適用於雙方需同步討論的少數情境；此時仍不釋出 HR `private_notes`。
- 只有 `hr` 能變更，建立職缺與後續編輯適用同一條規則；其他角色回 `403`。
- 該職缺一旦有任何面試紀錄正式提交，設定即鎖定，再變更回 `409`「已有面試提交紀錄，評分揭露規則不可變更」。用意是避免面試進行到一半才改變揭露條件，使先後兩位面試官在不同規則下評分而無法比較。
- 唯讀的 `blind_review_locked` 供前端先行停用控制項，但實際限制由後端執行。
- 變更會留下 `requisition.blind_review.update` 稽核紀錄。

驗收時須確認：非 HR 角色無法變更；已有提交紀錄的職缺無法變更；關閉盲評的職缺不會連帶洩漏 `private_notes`。API 欄位與錯誤碼見 [05-API規格書](05-API規格書.md) §5.1。

## 7. 題目版本與歷史不可覆蓋

1. 每份面試紀錄保存建立時的 `question_plan_id`、`question_plan_version` 及題目快照。
2. 整組重新產生或逐題重新產生都建立新版本；其他四題與舊版本保留。
3. 後續產生版本 2、3，不得改變已綁版本 1 的面試紀錄。
4. 重開舊面試紀錄仍沿用原版本，不能趁重開換綁新題組。
5. 若業務要用新版題目再面試，應建立新的面試 session／record，而不是改寫歷史。

題目如何由 Gemini／規則式流程產生、資料白名單、fallback 與啟用條件，統一見 [Gemini 客製化面試題目：實作與啟用規格](gemini-interview-question-preview.md)；本文件只定義題目建立後的評分、提交、修訂與盲評契約。

報表及匯出至少要帶出 stage、question plan version、interviewer 與 submitted／updated time，否則不同題組的分數可能被誤當成完全相同的量測。

## 8. API 操作範例

### 8.1 建立草稿

```json
{
  "stage": "hr",
  "question_plan_id": 123,
  "interviewed_at": "2026-08-05T10:00:00+08:00",
  "duration_minutes": 45,
  "mode": "video",
  "status": "in_progress",
  "questions": [
    {
      "question": "請分享一項跨部門合作成果。",
      "response": "",
      "rating": null,
      "not_asked_reason": null
    }
  ]
}
```

### 8.2 提交完成

```json
{
  "status": "completed",
  "questions": [
    {
      "question": "請分享一項跨部門合作成果。",
      "response": "協調產品與工程重新排定範圍。",
      "rating": 4,
      "not_asked_reason": null,
      "notes": "有清楚說明行動與結果。"
    },
    {
      "question": "如果意見仍不一致會如何處理？",
      "response": null,
      "rating": null,
      "not_asked_reason": "時間不足，留待主管複試"
    }
  ],
  "summary": "合作證據清楚；風險處理方式待主管複試確認。",
  "recommendation": "advance",
  "overall_rating": 4
}
```

### 8.3 重開

```http
POST /api/v1/applications/456/interview-records/789/reopen
Authorization: Bearer <stage owner token>
Content-Type: application/json

{"reason":"補正面試官誤選的分數"}
```

正常回應為 `200`、`status=in_progress`，且 `last_reopen_reason` 為去除空白後的理由。無權限為 `403`、找不到為 `404`、非完成狀態或完成後一般修改為 `409`、缺少／空白 reason 或其他欄位／提交規則不合法為 `422`。

## 9. 報表計算與禁止誤用

1. 未詢問題不得當成 0 分；逐題平均只使用有 `rating` 的題目，並同時顯示「已評 N 題／未詢問 M 題」。
2. `overall_rating` 是面試官整體判斷，與逐題平均分開顯示，不由系統自動覆寫。
3. HR 與主管的量表使用情境不同，未完成校準前不得用單一平均直接判定誰較嚴格或哪位候選人較好。
4. 題目版本不同時，報表須可分版本檢視；不可把新舊題組無標示混算。
5. 小樣本、缺答比例高或只完成單一階段時，報表要顯示資料不足，不提供看似精確的排名。
6. 不得把 `recommendation=offer`、高分或平均分門檻接成自動錄取／淘汰規則。
7. 若日後計算面試官一致性，應使用去識別化、最小必要資料，並先經 HR／法務核准，不拿來做未告知的員工績效處分。

## 10. UAT 最小驗收清單

- [ ] `completed` 每題無 rating／reason、同時填兩者、空白 reason、0 或 6 分均回 422。
- [ ] `completed` 缺 overall rating、recommendation 或非空 summary 均回 422。
- [ ] `response` 空白但 rating 合法時可完成。
- [ ] `planned`／`in_progress` 可保存不完整草稿；`cancelled`／`no_show` 不要求評分。
- [ ] 草稿只 PATCH `status=completed` 時，會用合併後整筆資料驗證，不能繞過必填。
- [ ] 完成後任何一般 PATCH 回 409；只有 stage owner 可重開。
- [ ] reopen request 缺 reason、空字串或只有空白時回 422；合法 reason 去除前後空白後保存。
- [ ] 新草稿 revision=0；首提 revision=1 且有 submitted at/by；重開維持 1；再提 revision=2 並更新 submitted at/by。
- [ ] 其他部門主管與 IT 讀取被拒；錯誤角色、IT／相容管理員的寫入與重開被拒。
- [ ] 雙方完成前，peer rating／reason／notes／summary／recommendation／overall／submitted by／last reopen reason 全部遮罩。
- [ ] 雙方完成後釋出；任一方重開後立即重新遮罩；HR 私人備註始終不釋出。
- [ ] 題目重新產生後舊面試仍指向原 plan ID／version；重開也不換版本。
- [ ] recommendation 為 offer／reject 不會自動修改 application status。
- [ ] create、update、reopen 均有稽核事件，且 audit details 不含完整回答或私人備註。
- [ ] 前端重新整理、跨帳號登入與直接 API 呼叫結果一致，無快取洩漏。

獨立 API 驗收檔：`backend/tests/test_interview_scoring_workflow.py`。

## 11. IT 後台與維運檢核

### 11.1 上線前

- migration 在 SQLite 測試及正式 PostgreSQL 演練均可 upgrade／downgrade；新增 JSON 欄位資料向後相容。
- 完整後端測試、Ruff、前端建置及瀏覽器 UAT 通過後才合併主線。
- 確認 audit retention、資料庫備份、還原演練與 API 回滾方案涵蓋新評分欄位。
- 權限測試必須使用 HR、該部門主管、其他部門主管、IT／管理員五種情境。

### 11.2 上線後監控

- 監看完成提交的 `422`、完成後修改的 `409`、越權的 `403` 與重開頻率，但不要把回答內容或私人備註寫入應用程式 log。
- 稽核應記錄動作、record/application/stage、操作者、部門、欄位名稱與狀態變更，不複製候選人逐字回答。
- system issue tracker 只放問題與驗收步驟，模型已明定不得存候選人資料。
- 若同一紀錄短時間多次重開、跨部門 403 異常增加或 completed 紀錄遭非 reopen 修改，應觸發告警與調查。

## 12. 公平性、隱私與發布阻擋項

| 等級 | 風險 | 必要處置 |
|---|---|---|
| 阻擋 | `not_asked_reason` 在雙方完成前未遮罩，可能透露對方判斷 | 與 rating／notes 同步遮罩，加入 API 與瀏覽器測試 |
| 阻擋 | completed 只在前端鎖定，可用 API 覆寫歷史 | 後端 PATCH 回 409；僅稽核化 reopen 可解鎖 |
| 阻擋 | 重開未檢查 stage owner 或部門，可跨部門改寫 | 重用 application scope 與 stage 權限，測 403 |
| 阻擋 | 新題目版本覆蓋舊面試或重開時換綁版本 | plan ID／version 不可 PATCH，歷史與逐題版本測試須通過 |
| 阻擋 | 高分／offer 建議自動改 application status | 分離評分與招募決策端點，驗證狀態不變 |
| 阻擋 | 報表把未詢問題當 0 分，系統性懲罰時間不足或不同流程 | 排除分母並顯示未詢問數與原因分布 |
| 高 | 共享 `response` 中夾帶面試官結論，實質破壞盲評 | UI 提示只記錄候選人證據；UAT 檢查用語與快取 |
| 高 | 自由文字寫入健康、家庭、宗教等敏感資訊 | 法遵提示、權限、稽核與教育訓練；報表不匯出不必要文字 |
| 高 | 不同題目版本／不同職缺分數直接排名 | 報表帶版本與職缺，未校準不做跨組比較 |
| 中 | 小樣本平均被當作準確率或錄取品質 | 顯示樣本數、缺答率與資料不足警告 |

前六項未通過不得發布正式環境。其餘高風險項至少要有明確 UI 提示、教育訓練與 UAT 證據。
