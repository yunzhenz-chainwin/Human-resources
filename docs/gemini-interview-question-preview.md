# Gemini 客製化面試題目：實作與啟用規格

> TalentHub 已具備 Gemini 選配路徑，但 `GEMINI_ENABLED` 預設為 `false`；未啟用、未設定 API key、逾時、配額不足或格式驗證失敗時，一律回退可追溯的規則式題目。送往 Gemini 的候選人資料採嚴格白名單，不含姓名、聯絡方式、地址、生日、公司／學校名稱或自由文字經歷。

**更新日期**：2026-08-27

**文件定位**：本文件只維護「題目如何產生與安全啟用」。題目建立後的 1–5 分、未詢問原因、提交鎖定、修訂及雙方盲評，以 [13-結構化面試評分與盲評操作規格](13-結構化面試評分與盲評操作規格.md) 為準；是否已發布以 [07-開發時程與里程碑](07-開發時程與里程碑.md) 為準。

## 目前畫面應呈現的兩階段

### HR 初談（固定評估面向，所有候選人可比較）

未產生題組前，畫面直接顯示全公司相同的 HR 標準五題。HR 可按「重新產生」改寫問法（Gemini 或規則式備援），但五個評估面向與難度固定：求職動機、職務期待、合作溝通、壓力應對、到職條件；客製化只能提供具體情境，不改變錄用標準。主管可以讀取 HR 的問答，但不能修改 HR 紀錄。

### 部門主管面談（依職缺與履歷客製）

固定產生 5 題，評估面向依序為：經驗轉移、專業能力、成果深挖、能力風險、到職情境。題目內容以「職缺職稱與必要技能 + 結構化履歷事實（職稱、總年資、技能、各段職稱／年資）」為依據；依人格特質產生的題目屬於另一個「特質面試題建議」功能，不進入這份五題題組。每題都顯示：

- 設計依據（`source`，例如：職缺必備技能、最近一份職稱）
- 提問目的（`purpose`）
- 建議追問（`follow_up`）
- 產生方式（規則式／Gemini）與法遵標記（觸及受保護特徵時顯示警告與改寫建議）

HR 與主管雙方都能讀取完整問答與進度；只有該階段的紀錄者能編輯自己的回答與評分。產題權限依階段區分：HR 產生／重產 HR 題組，部門主管產生／重產主管題組，其他角色回 `403`。兩個階段都可只重新產生單一題目（第 1–5 題擇一），其餘四題與歷史版本保留。

## 預覽範例（不呼叫 Gemini）

輸入資料（已去識別化，只保留工作相關欄位）：

```json
{
  "job_title": "企業客戶經理",
  "required_skills": ["B2B 業務", "CRM", "提案簡報"],
  "candidate": {
    "current_title": "客戶成功經理",
    "total_years": 6,
    "skills": ["B2B 業務", "Salesforce", "提案簡報"],
    "experience_roles": [
      {"title": "客戶成功經理", "years": 4}
    ]
  }
}
```

預覽會顯示類似下列的主管題目：

1. 你的履歷列有客戶成功經理與 B2B 業務技能；請選一個你實際參與的棘手客戶案例，說明你如何界定問題、推進決策並驗證結果？
   - 依據：結構化職稱／B2B 業務技能
   - 目的：確認客戶經營、問題拆解與結果導向
   - 追問：若客戶仍未續約，你會先檢查哪三個訊號？

2. 這個職位需要使用 CRM 管理商機，履歷技能列有 Salesforce。請分享一個你實際使用 CRM 的例子，以及如何確保資料品質？
   - 依據：職缺必備技能 CRM + 履歷技能 Salesforce
   - 目的：驗證工具熟練度與流程紀律
   - 追問：遇到業務不更新資料時，你會怎麼處理？

3. 履歷技能列有提案簡報；請提供一個實際跨部門提案案例，說明你如何讓參與者對成功標準達成共識？
   - 依據：職缺技能提案簡報 + 履歷技能提案簡報
   - 目的：確認溝通結構與協作方式
   - 追問：若兩個部門的優先順序衝突，你如何推進？

題目帶入面試紀錄後可由面試官編輯；題組版本保留原始草稿（舊版本不可覆蓋），面試紀錄則保存最後修改者與時間，方便稽核與公平性比較。重新產生單題時，已有作答、評分或手動修改的題目不會被前端自動覆蓋。

## Gemini 啟用方式（程式已實作，正式啟用仍需核准）

後端新增 `GEMINI_API_KEY` 與可選設定：

```text
GEMINI_API_KEY=只放在後端環境變數，不放前端、不提交 Git
GEMINI_MODEL=gemini-3.6-flash
GEMINI_ENABLED=false
GEMINI_TIMEOUT_SECONDS=45
GEMINI_MAX_OUTPUT_TOKENS=4096
GEMINI_DAILY_GENERATION_LIMIT_PER_USER=50
```

API key 不需要提供給我或寫入聊天內容。部署時請放在主機的 `.env`、Docker secret 或 Windows 服務環境變數，並限制只有後端程序可讀；前端只能呼叫 TalentHub 後端，不能直接呼叫 Google API。

建議流程：

1. 預設由現有規則式產生 5 題，立即可用且可測試。
2. 若 `GEMINI_ENABLED=true`，後端只將職缺名稱、必要技能（最多 12 項），以及候選人的職稱、總年資、技能（最多 12 項）與各段職稱／年資（最多 6 段）送 Gemini；自由文字 JD、經歷描述、公司／學校與聯絡資料不會送出。每個欄位還須通過結構化標籤檢查，Email、電話、身分證字號、網址、地址等樣式會被遮蔽或整欄排除。
3. 後端以 `responseJsonSchema` 要求固定題數與評估面向：整組須恰好 5 題、單題重產恰好 1 題，且指定面向各出現一次、`question`／`purpose`／`follow_up`／`source` 皆非空、題目不得重複；不符即視為無效回覆並回退規則式題目。每題另以台灣就服法／性平法規則庫檢查，觸及婚姻、懷孕、年齡、性別、宗教、健康等受保護主題時標記警告與改寫建議，供人工覆核修改。
4. 驗證失敗、逾時、配額不足（上游 `429`，並啟動 15 分鐘冷卻）、模型不可用或沒有 API key 時，自動回退規則式題目並在畫面顯示原因（`generation_warning`），不影響面試流程。
5. 題組每個版本保存 prompt 版本對應的 context hash、模型、產生方式、產生者與 token 用量（輸入／輸出／思考）；人工修改保存於面試紀錄的題目快照，不覆蓋題組版本。log 與稽核不保存原始 PII。

### 用量控管與 source 長度

- 相同輸入（context hash 未變）重新整理不會再次呼叫 API，直接載入已保存題組；強制重新產生與單題重產會略過 24 小時快取。
- 每位使用者每日產生次數受 `GEMINI_DAILY_GENERATION_LIMIT_PER_USER`（預設 50）限制：計算自 UTC 午夜以來由該使用者建立的題組版本數（整組與單題重產都計入），超過回 `429` 並帶 `Retry-After`（重置點為 UTC 午夜，即台北時間 08:00）。僅在 Gemini 啟用且已設定 API key 時檢查；純規則式產生不受限。
- 每題 `source`（設計依據）無論 Gemini 或規則式產生，一律正規化空白並截斷至 200 字元（migration `a9e3d51c7b82` 已回填舊題組），避免帶入面試紀錄提交時被 `422` 擋下。

## 實際的 Gemini 回傳格式

```json
{
  "questions": [
    {
      "category": "專業能力",
      "question": "...",
      "purpose": "...",
      "follow_up": "...",
      "source": "職缺必備技能：CRM；履歷技能：Salesforce"
    }
  ]
}
```

後端接受上述 `{"questions": [...]}` 信封或直接的 JSON 陣列；`category` 必須是該階段五個固定面向之一（常見別名如「核心技能」會正規化回「專業能力」）。保存時 `source` 會加上「Gemini 客製題目｜」前綴並套用 200 字元上限。題目本身不應推測人格或家庭、健康、年齡等非工作因素；讀取舊題組時，法遵標記一律以最新規則庫重新計算，不沿用保存時的判定。

## 正式啟用前驗收

正式啟用 Gemini 前，應以去識別測試資料檢查 HR／主管兩階段題組與逐題重新產生：確認傳送內容只有白名單欄位、其他四題與歷史版本不被覆蓋、敏感問題被法遵規則標記，並驗證逾時／錯誤格式會回退規則式結果、超過每日產生上限回 `429` 且帶 `Retry-After`。只有通過 UAT 的題組才套用至面試紀錄。對應自動化契約：`backend/tests/test_interview_questions.py`。
