# 媒合小樣本基準：操作與指標說明

## 目的與限制

這套基準用 50 組可重建的「合成職缺 × 合成履歷」案例，讓 HR 與部門主管在看不到系統分數的情況下獨立判斷，再比較人工排序與目前媒合規則。案例不含姓名、電話、Email、地址或真實履歷內容，也不會寫入正式人才庫、職缺、應徵或媒合結果資料表。

這是小樣本流程基準，不是錄取預測模型。報表只能用來找出閘門錯殺、排名偏差、技能同義詞缺口與資料不足等問題，不可對外宣稱為真實錄取準確率。

## 案例組成

固定資料集包含 5 類職缺，每類 10 位合成候選人，共 50 組：

- 後端工程、前端工程、資料分析、人才招募、B2B 業務。
- 明確適合、另一種明確適合、邊界人選、技能同義詞、轉職可轉移經驗。
- 資料缺漏、薪資不符、地點不符、年資不足、明確不適合。

fixture 位於 `backend/app/fixtures/matching_benchmark_v1.py`，固定 key 與版本用來確保每次建立的案例完全一致。若日後修改案例內容，必須建立新的 suite key／版本，不可改寫已有人工作答的舊資料集。

## 安裝與建立資料

1. 套用 migration：

   ```powershell
   cd C:\Users\Administrator\Human-resources\backend
   python -m alembic upgrade head
   ```

2. 在 development 或 test 環境建立／重算基準：

   ```powershell
   python -m scripts.seed_matching_benchmark
   ```

3. 需要機器可讀結果時：

   ```powershell
   python -m scripts.seed_matching_benchmark --json
   ```

seed 可以重複執行：相同 fixture 不會增加 suite 或案例，只會以目前媒合規則重新計算隱藏分數。`APP_ENV=production`、`prod` 或 `staging` 時會直接拒絕執行。

## 盲評流程

1. HR 登入後逐一閱讀職缺條件和合成履歷，選擇「適合面試／可考慮／不適合／資料不足」。
2. 每題至少選一個結構化原因；選「資料不足」時必須包含「資訊不足」。
3. 「優先序 1–10」是選填項目，同一職缺不可重複；可用來打破相同分類的排序。
4. 部門主管用自己的帳號完成同一批題目。兩個角色只能看到自己的作答，均看不到系統分數、必要條件閘門、測試情境和設計標籤。
5. 至少一位 HR 與一位主管各自完成全部 50 題後，HR 才能揭盲。
6. 揭盲後評分鎖定，報表才會顯示系統分數、閘門、人工分類及案例設計標籤。

## 指標定義

| 指標 | 定義 | 最低資料門檻 |
|---|---|---|
| HR／主管 Top-5 overlap | 每個職缺的系統前五名與該角色盲評前五名交集比例 | 至少 3 個完整職缺群組（15 個名次） |
| Top-5 false negative | 人工前五名中未進入系統前五名的比例 | 同上 |
| Gate miss | 人工判為「適合面試／可考慮」，但系統必要條件未通過的比例 | 至少 5 個人工正向案例 |
| 角色一致率 | HR 與主管對同一案例給出完全相同四分類的比例 | 至少 10 組成對評分 |
| 資料完整度 | 履歷七項資訊維度的平均完整度，0–100 | 至少 20 個案例 |

分母未達門檻時，API 回傳 `status=insufficient_data` 且 `value=null`。前端顯示「未知」，不會把未知資料誤畫成 0%。

若同一角色有多位評審，報表使用角色內多數決；票數平手的案例視為未知。完整評審少於兩位時會顯示個人偏好風險警告。

## API

所有路徑位於 `/api/v1/matching-benchmark`：

- `GET /suites`：基準清單與兩角色完成度。
- `GET /suites/{suite_key}/cases`：盲評案例，只回傳自己的評分，不含任何系統結果。
- `PUT /suites/{suite_key}/cases/{case_key}/my-rating`：新增或更新自己的評分。
- `POST /suites/{suite_key}/reveal`：HR 在兩角色完成後揭盲。
- `GET /suites/{suite_key}/report`：揭盲後報表；揭盲前回傳 409。

## 系統整合位置

- 後端已在 `backend/app/api/router.py` 掛載盲評 API，並套用招募角色驗證。
- 三個 benchmark model 已註冊到 Alembic metadata，可由 `alembic check` 檢查 schema 漂移。
- 前端位於「媒合程度」頁面的「小樣本驗證」分頁；「正式媒合」與盲評資料不會混在一起。
- 本機 development 資料庫已建立 50 組固定案例。production／staging 保持空表，seed 指令會直接拒絕執行。
